# v0.63 / Mission Run Session Affinity + Scoped Review Focus

提交信息：`v0.63: 绑定 Mission 会话与复核聚焦`

## 版本分配依据

v0.62 已把 Agent Loop 推荐动作收紧到 request、envelope 与固定推荐集合的三方交集；当前下一项独立的 presentation-layer 正确性缺口是 Mission Run 的身份关联。`ClawStore.missionRunSummary` 目前分别取 `clawMobileTasks.first` 和 `clawGatewaySessions.first`，没有验证 `session.taskID == task.id`；SwiftUI compact 与 regular 布局又只保存裸 `focusedReviewKind`。因此新任务出现时，Mission Run 可能把新 task 的风险、审批与旧 session 的状态、artifact、metadata review 拼在一起；即使新旧 Mission 都有同名 `delivery-safety` 等 review kind，旧聚焦也会被错误继承。该修复不改变 Gateway 或协议 schema，适合作为 v0.63 的独立展示层一致性版本。

## 背景与问题定义

- `ClawMobileTask.id` 是手机端任务身份，`ClawGatewaySession.taskID` 是 session 到 task 的现有结构化关联。
- `ClawAutonomousLoopState` 已有可选 `taskID` 和 `sessionID`，但 Mission Run 当前没有统一 resolver 使用这些身份。
- `ClawMissionRunSummary` 当前没有 Mission scope 身份，无法判断一个本地 review focus 是否仍属于当前任务回合。
- `PhoneAgentCompactLayout` 和 `PhoneAgentWorkbenchLayout` 都保存 `String?`；regular 左右栏共享该字符串，但字符串不包含 Mission 身份。
- `activeReviewFocus(from:)` 只检查同名 review kind 是否仍存在。新 Mission 复用同名 kind 时，旧 focus 会继续过滤详情，用户无法知道证据已经换了任务回合。
- `missionRunLiveGatewayHealthStrip` 也必须服从同一 Mission 关联边界，不能在新 task 尚无匹配 session/request 时继续展示旧 session 的运行状态。

## 目标

1. 为 Mission Run 建立单一、可测试的 task/session resolver；当前 summary 的 task、session、live request 和 session events 必须属于同一个 taskID 关联域。
2. 当前 Mission 以最新 task 为展示基准；`autonomousLoop.taskID/sessionID` 只能帮助解析该当前 task 的精确 session，不能让旧 loop 引用覆盖更新的 task。
3. session 只有在 `session.taskID == selectedTask.id` 时才能进入 summary；优先使用与当前 task 匹配且由 `autonomousLoop.sessionID` 精确指向的 session，否则使用该 task 的最新匹配 session。
4. 当前 task 尚无匹配 session 时，summary 只显示该 task 的发送前状态；所有 session 结果计数、artifact、metadata review、Gateway 状态和 session 派生摘要必须为空、零或发送前状态，不能回退到任意旧 session。
5. 给 Mission Run 增加仅供本地 presentation 使用的 scope 身份：发送前以 task ID 为 scope，存在匹配 session 后以 session ID 为 scope；idle 时 scope 为空。
6. 用 `ClawMissionRunReviewFocus`（Mission scope + review kind）替换 SwiftUI 中裸 `String?` 聚焦状态。compact iPhone 和 regular iPad/mac 必须复用同一个类型和相同解析语义。
7. 同一 scope 内的有效聚焦继续保留；task 改变、task 从发送前进入 session、或 session 改变时，旧 focus 必须失效，即使新 Mission 也包含同名 review kind。
8. scope 失效时 fail closed：不继续筛选单项详情，恢复全量 detail rows，并在 Focus Context 或 Review Detail Dock 显示固定的“Mission 已更新，旧聚焦已失效”类提示；用户重新选择后才建立新 scope 的 focus。
9. Mission ID 只用于内存关联和测试，不在可见文本、chip、按钮、日志描述、accessibility label 或 envelope 中显示完整 UUID。
10. 保持所有 Mission Run 展示为 metadata-only；不得读取 artifact `reference`、Gateway `file://` payload 或 `auditTrail` 原文来判断关联或补全详情。

## 非目标

- 不修改 Gateway、Gateway simulator、Gateway fixture 或 Node smoke 行为。
- 不新增或修改 envelope schema、action kind、event kind、artifact kind、artifact metadata key 或 Gateway wire contract。
- 不改变 planner、bridge、审批、发送、重试、自动循环或真实执行权限。
- 不新增跨启动持久化 focus、跨设备 focus 同步、历史 Mission 浏览器、深链导航或完整 artifact payload viewer。
- 不根据 command 文本、时间接近度、artifact 内容、workspace path 或自然语言猜测 task/session 关系；关联只使用结构化 UUID 字段。
- 不把完整 task/session/scope UUID 显示给用户，也不把它写入新的协议字段或 metadata。
- 不顺手重构所有 Mission Run 派生摘要，不修改无关 Xcode 工程或用户 scheme 文件。

## 当前架构证据

- `Claw/Services/ClawStore.swift` 的 `missionRunSummary` 当前直接使用 `clawMobileTasks.first` 与 `clawGatewaySessions.first`，随后把两者共同传入 phase、primary action、计数、artifact review、approval queue 和 action preflight 派生。
- 同文件 `gatewayLiveHealthSummary` 当前也直接使用最新 session；其 `ClawGatewayLiveRequest.taskID`、event `sessionID/taskID` 已提供结构化过滤依据。
- `Claw/Core/ClawModels.swift` 中 `ClawMobileTask.id`、`ClawGatewaySession.taskID`、`ClawAutonomousLoopState.taskID/sessionID` 已存在，不需要新增 wire schema。
- `ClawMissionRunSummary.activeReviewFocus(from:)` 当前只接受 `String?` 并按 review kind 是否存在判断有效性；`reviewDetailDockSummary(focusedOn:)` 只能识别未知 kind 过期，不能识别跨 Mission 的同名 kind。
- `Claw/Views/ContentView.swift` 中 `PhoneAgentCompactLayout` 与 `PhoneAgentWorkbenchLayout` 都声明 `@State private var focusedReviewKind: String?`；regular 左侧 `ClawMissionRunPanel` 与右侧 `ClawMissionReviewDetailDockView` 共享同一个裸字符串 binding。
- `ClawTests/ClawTests.swift` 与 `Tools/LogicSmoke.swift` 已对 Mission Run 聚焦、状态项回退、过期 kind 和 metadata 脱敏做大规模对称覆盖，可在现有测试段落旁加入 session affinity 和 scope 变化回归。

## 详细实现步骤

### 1. 建立统一 Mission resolver

在 `ClawStore` 内新增一个私有、纯派生 resolver（可用私有 tuple 或私有小结构），一次性返回当前 Mission 的 `task`、匹配 `session`、匹配 live request 和该 session 的 events。不要让各 computed property 各自重新选择“最新”对象。

解析规则必须固定：

1. 当前展示 task 以 `clawMobileTasks.first` 为基准；若要使用 `autonomousLoop.taskID`，只能在它解析到同一个当前 task 时作为一致性证据，不能选择一个已经被更新 task 排在后面的旧任务。
2. 没有 task 时，不得凭旧 session 构造一个混合 Mission；返回 idle scope 和空 session 派生数据。
3. 若 `autonomousLoop.sessionID` 能解析到 session，只有该 session 同时满足 `session.taskID == selectedTask.id` 才可优先采用。
4. 精确 session 引用不存在、不匹配或已过期时，只能在 `clawGatewaySessions` 中选择 `taskID == selectedTask.id` 的最新 session；绝不能 fallback 到列表中任意 session。
5. live request 只有在 `request.taskID == selectedTask.id` 时才属于当前 Mission；Gateway events 只取已选 session 的 `sessionID`，并在可用时继续核对 taskID。
6. 所有 Mission Run 入口必须消费同一 resolver 结果，包括 phase、command、primary action、stage track、status line、result counts、artifact kinds、所有 metadata review、priority/approval/preflight 派生，以及 `missionRunLiveGatewayHealthStrip`。

如当前 live health 工厂需要 request、connection state、events 和 latestSession，给它传入 scope 过滤后的值。当前 task 尚无匹配 session/request 时使用空事件和无旧 session/request的安全基线，不得显示上一 Mission 的 completed、fallback、error、ping 或 artifact 状态。

### 2. 给 Summary 增加本地身份证据

在 `ClawMissionRunSummary` 增加最小的本地 presentation 身份字段，建议至少包括：

```swift
var missionScopeID: UUID?
var taskID: UUID?
var sessionID: UUID?
var sessionTaskID: UUID?
```

约束：

- idle：四者均为 `nil`。
- 发送前 task：`taskID` 与 `missionScopeID` 为 task ID，session 字段为 `nil`。
- 有匹配 session：`taskID == sessionTaskID`，`sessionID` 为 session ID，`missionScopeID == sessionID`。
- 这些字段只用于本地派生、SwiftUI 状态关联和测试断言；不得插值到任何用户可见文本或 accessibility 文案。
- 这是 App presentation model 的内部演进，不得写入 `ClawMobileEnvelope`、`ClawGatewayEvent` 或 artifact metadata。

如果现有 memberwise initializer 的调用点较多，可使用明确默认值或局部 initializer 收敛改动，但不能用默认值掩盖 Store 未传正确身份。

### 3. 定义 Mission-scoped focus

在 Swift presentation model 层新增：

```swift
struct ClawMissionRunReviewFocus: Equatable, Sendable {
    var missionScopeID: UUID
    var reviewKind: String
}
```

除非现有状态保存确实需要，否则不要增加持久化或 wire 编码职责。compact 和 regular 布局都改为：

```swift
@State private var reviewFocus: ClawMissionRunReviewFocus?
```

并把 `Binding<ClawMissionRunReviewFocus?>` 贯穿 `ClawMissionRunPanel`、`PhoneAgentReviewColumn` 和 `ClawMissionReviewDetailDockView`。regular 左右栏继续共享同一 binding；compact 使用同一类型而不是另建一套逻辑。

### 4. 集中解析 focus 有效性

为 `ClawMissionRunSummary` 提供 scope-aware helper，例如：

```swift
func activeReviewFocus(from requestedFocus: ClawMissionRunReviewFocus?) -> String?
```

必须先验证：

```text
requestedFocus.missionScopeID == summary.missionScopeID
```

再验证 `reviewKind` 是否仍存在于 priority queue 或 available detail review。scope 不同永远返回 `nil`，不能因为新 Mission 有同名 kind 而重新激活。

为避免现有十余个 `focusedOn: String?` 派生 helper 大范围重写，可以在视图入口只解析一次 active kind，再把该 active kind 传给既有摘要；但以下两个需要知道“曾请求 focus 但 scope 已失效”的摘要必须接受 scoped focus 或等价的显式 stale 标志：

- `focusContextSummary`
- `reviewDetailDockSummary`

它们要区分：无 focus、同 scope 有效 focus、同 scope 但 kind 过期、跨 scope 过期。跨 scope 时 `activeReviewKind=nil`、`showsFocusedDetailOnly=false`、detail rows 为全量、`hasStaleFocus=true`，并使用固定脱敏提示说明 Mission 已更新。不得把旧/new scope UUID 放入提示。

### 5. 更新聚焦交互

- 所有 row/button 的 focus 回调仍只传固定 `reviewKind`；容器收到点击时使用当前 `summary.missionScopeID` 组装新的 `ClawMissionRunReviewFocus`。
- 当前 summary 没有 scope 时，不创建 focus。
- 清除按钮把 scoped focus 设为 `nil`。
- Mission scope 变化时不要把旧 focus 静默映射到新 scope。可以保留旧值让摘要显示 stale 提示，也可以在明确展示一次 stale 状态后清除；无论选择哪种实现，当前 active kind 必须立即为 nil，右侧 Dock 和 compact detail rows 必须立即恢复全量。
- task 发送后从 task scope 切换为 session scope，应视为一次 scope 变化；发送前建立的 `approval` 或其他 focus 不得自动继承到 session。
- 同一 session 收到后续 event 或 metadata 更新时 scope 不变，合法 focus 应保持。
- regular 左右栏必须同时看到相同的 active/stale 解析结果，不能一栏清除而另一栏继续过滤。

### 6. 保持展示与隐私边界

- 关联只看 UUID 等结构化字段，不读取 `artifact.reference`、`file://`、payload、`auditTrail` 原文、command 内容或 metadata 自由文本。
- 旧 session 即使含 token、URL、完整路径、header、command、草稿或 `toolArguments`，新 task 的 summary、Focus Context、Dock、Control Snapshot、Operator Strip、各 board/deck/timeline/gate/radar/brief 和 accessibility label 都不能出现这些值。
- 不显示完整 UUID，也不要新增“短 UUID chip”；本轮身份只用于正确性，不是面向用户的诊断信息。
- 不自动审批、发送、重试或继续 loop；focus 仍然只是本地详情筛选。

## XCTest 与 LogicSmoke 对称测试

`ClawTests/ClawTests.swift` 和 `Tools/LogicSmoke.swift` 必须对称覆盖同一组行为，不能只测 helper 而不测 Store 的真实 resolver：

1. **A 完成、B 未发送**：先让任务 A 产生完成或需处理 session 和 artifact，再创建最新任务 B 但不发送。B 的 summary command、risk、approval、phase 来自 B；`sessionID/sessionTaskID` 为空；succeeded/failed/retryable/artifact count 为 0；artifact kinds 和全部 Gateway metadata review 为 nil/空；不得混入 A 的 session status、review queue 或 live health。
2. **task/session 一致性**：只要 summary 同时有 task 与 session 身份，就断言 `summary.taskID == summary.sessionTaskID`；选中的 session 必须是该 task 的 session。
3. **精确 session 与 fallback**：同一 task 存在多个 session 时，合法 `autonomousLoop.sessionID` 精确选择对应 session；引用缺失或指向其他 task 时，只能选择当前 task 的最新匹配 session，绝不能选择全局最新的不匹配 session。
4. **无匹配 session fail closed**：当前 task 存在、全局也有旧 session，但没有 taskID 匹配时，所有 session 派生数据保持空/零，phase 不得被旧 session 的 completed/blocked/needsAttention 覆盖。
5. **同 scope focus 保留**：在同一 task scope 或同一 session scope 内，`delivery-safety` 等有效 focus 继续生效，Dock 只显示对应 detail，左右栏使用相同 focus 类型。
6. **新 task 令同名 focus 失效**：任务 A 聚焦 `delivery-safety`，创建同样也有 `delivery-safety` 的任务 B；旧 focus 的 scope 与 B 不同，`activeReviewFocus` 必须为 nil，Dock 标记 stale，恢复全量详情，不能把同名 kind 当作仍有效。
7. **task 到 session 的 scope 切换**：发送前 task scope 上的 focus 在 session 建立后失效；`missionScopeID` 从 task ID 变为 session ID，Dock/Focus Context 回退全量并提示旧聚焦失效，用户重新选择后才恢复单项详情。
8. **新 session scope**：同一 task 若创建新的 session，旧 session focus 不得自动继承；旧 focus stale，新 focus 可正常建立。
9. **敏感旧证据隔离**：给 A 的 artifact metadata、reference 或 audit text 注入可识别 token、`file://` 路径、URL/header/command 字符串，再创建 B。收集 B summary 及所有主要派生摘要的可见字段和 accessibility 文案，断言均不包含注入值和 A 的完整 UUID。
10. **idle 与非法 focus**：idle 没有 scope；不能创建 active focus。scope 相同但未知 kind、scope 不同但 kind 相同都必须 fail closed，并保持现有状态项/未知项全量回退语义。

测试可以新增最小 internal test helper 来构造 task/session，但不得放宽生产 setter、删除既有断言或依赖 `file://` payload 内容。若现有公共操作足以产生 A/B 场景，优先走 `ClawStore` 的真实方法，确保回归能捕获独立取 first 的原始缺陷。

## 风险

- 只在 `missionRunSummary` 过滤 session、却让 live health 或某个 review helper继续读取全局最新 session，会保留隐蔽的跨 Mission 污染；所有 Mission Run 入口必须共用 resolver。
- 只检查 `reviewKind` 是否存在而不检查 scope，会让同名 `delivery-safety`、`shell-safety` 或 `approval` 跨任务继承。
- 在 scope 变化时仅清掉右栏或仅清掉 compact 状态，会造成 iPad/mac 左右栏分叉；binding 类型和解析必须统一。
- 发送前 task scope 到 session scope 的切换是预期失效点；若继续使用 task ID 作为发送后 scope，旧 focus 会错误延续到新证据。
- 把 UUID 加到 chip、日志、VoiceOver 或调试提示会违反展示边界；测试必须扫描可见派生文本。
- 通过 command、createdAt 或 artifact 内容推断关联会在重复命令和并发 session 下出错；只允许结构化 ID。
- 为测试方便开放 `private(set)` 状态或读取 payload 会扩大生产边界，应使用最小 internal fixture/helper 或现有 Store 操作。

## 禁止项

- 禁止修改 Gateway、Gateway JS smoke、simulator/fixture、envelope schema、action kind、event kind、artifact kind 或 artifact metadata contract。
- 禁止读取或展示 artifact `reference`、Gateway `file://` payload、`auditTrail` 原文、raw token、Authorization/header、URL/path、command/stdout/stderr、diff、草稿正文或 `toolArguments`。
- 禁止在 UI、accessibility、日志或文档示例中展示真实完整 task/session/scope UUID。
- 禁止通过自然语言、时间或 payload 猜测 task/session 关联。
- 禁止自动审批、自动发送、自动重试、自动继续 Agent Loop或扩大桌面执行权限。
- 禁止删除/弱化既有断言、伪造测试通过、把本地静态检查称作业务验证，或跳过 Agent C artifact 复判。
- 禁止本地编译、build、xcodebuild、Swift logic smoke、Gateway smoke 或 `node --check`。
- 禁止回滚、覆盖或提交用户/其他 Agent 的无关改动，特别是现有 Xcode 工程与 scheme 用户文件。
