# v0.64 Gateway Unsupported Action Fail Closed

## 版本号与分配依据

- 版本号：`v0.64`。
- 阶段：`v0（核心智能能力）`。
- 版本名称：`GatewayUnsupportedActionFailClosed`。
- 提交信息固定为：`v0.64: 阻断 Gateway 未支持动作`。
- 分配依据：v0.62 已约束 Agent Loop 推荐动作必须落在 request、envelope 与 Gateway 固定支持推荐集合的交集内，但真实 action 执行入口仍存在独立缺口。当前 `ClawMobileActionKind` 包含 21 个 schema 可表示动作，`Tools/claw-gateway-server.mjs` 的固定 handler 只实现其中 9 类；当一个已知但未实现的 action 同时被 envelope `allowedActionKinds` 放行时，`runAction` 的 `default` 会进入 `genericAuditAction`，写入包含 action 输入的审计 payload，并返回 `status: "succeeded"`。这会把“没有执行器”错误报告成成功，破坏 action-bound 审计、手机端结果可信度和后续智能循环的证据基础，因此作为 v0.64 单独修复。

## 背景与当前架构依据

- `Claw/Core/ClawModels.swift` 的 `ClawMobileActionKind` 同时描述手机本地动作、Gateway 动作和禁止占位动作；其中包括 `analyzeLocalContext`、`requestPermission`、`readContacts`、`createReminder`、`scheduleNotification`、`openExternalURL`、`runShortcut`、`speechCapture`、`backgroundRefresh`、`desktopHandoff`、`auditLog`、`blockedUnsupported` 等当前 Node Gateway 没有固定执行 handler 的 kind。
- `Tools/claw-gateway-server.mjs` 的 `actionPolicy` 当前只检查 action 是否 blocked 和是否命中 envelope `gateway.allowedActionKinds`，没有检查固定 handler 支持集合。
- 同文件 `runAction` 的显式 handler 仅覆盖 `runAgentLoop`、`observeScreen`、`controlBrowser`、`manageFiles`、`runShellCommand`、`extractData`、`operateDesktopApp`、`composeMessage`、`composeEmail`；`default` 调用 `genericAuditAction` 并返回 succeeded。
- `genericAuditAction` 当前会把 `instruction`、`inputPreview`、`target` 和完整 `toolArguments` 写入 artifact payload。对未支持 action 来说，这既不是实际执行证据，也扩大了敏感输入落盘面。
- `buildGatewayEvents` 已为每个 action 生成 action-bound `actionStarted`、artifact event 和最终状态 event，并在所有 action 后生成 `sessionCompleted`。本轮应复用该事件协议，不新增 event kind。
- `Tools/ClawGatewayEventFixture.swift` 当前也把多数无 Node handler 的 enum case 视为 `.succeeded` 并生成通用 `auditLog`，会继续制造与真实 Gateway 相同的 false-success，必须与 v0.64 合同对齐。
- `Tools/claw-gateway-direct-smoke.mjs` 和 `Tools/claw-gateway-smoke.mjs` 已覆盖真实 handler、policy block、action-bound failure、artifact 落盘和 session completion，可加入一个已知 enum 但固定 handler 未支持的最小 envelope 场景。
- Swift 现有 `ClawGatewayActionResultStatus.failed`、`ClawGatewayEventKind.actionFailed`、session reducer、结果计数和通用 artifact metadata review 已能表达该失败。除非实现复核时证明现有路径无法呈现，禁止为了本轮新增 wire schema、状态枚举或大型 UI。

## 目标

1. Gateway 对 schema/action enum 中存在、envelope allowlist 明确允许、但当前固定 handler 集合不支持的 action 必须 action-bound fail closed，绝不能返回 `succeeded` 或 `actionCompleted`。
2. 固定 handler 支持集合必须成为 Gateway 内单一、可复用的策略来源，并与 `runAction` 的实际显式分派保持一致；新增 handler 时不能只改 switch 而遗忘策略集合，或只改集合而没有实现分派。
3. unsupported handler 结果固定为 `failed`、`actionFailed`、`isRetryable=false`，使用稳定、非用户输入派生的 reason/diagnostic，例如 `unsupported_action_handler`；不得伪装成审批阻断、envelope allowlist skip 或临时基础设施错误。
4. 每个 unsupported action 必须产生一个与原 `actionID/actionKind` 绑定的既有 `auditLog` artifact，明确记录 schema 已接受、envelope 已授权、handler 不支持、handler execution blocked、business side effects not attempted，以及不可重试结论。
5. unsupported audit payload 与 metadata 必须脱敏且最小化：可以记录 action ID、已知 action kind、固定 policy/diagnostic、布尔值和固定 safety flags；不得记录或回显 `instruction`、`inputPreview`、`target`、`toolArguments`、URL、host、path、workspace path、command、args、正文、联系人、token、header、cookie、secret 或任意用户输入派生字符串。
6. unsupported action 在任何 browser/file/shell/desktop/message/agent-loop handler 和任何对应业务 artifact 写入之前被阻断。除最小审计 artifact 外，不得产生业务副作用、网络请求、Shell 执行、文件写入、桌面自动化、草稿生成或 AgentTrace 推荐。
7. 只失败当前 unsupported action；事件序列保持单调且会话继续处理后续合法 action，最终仍可产生 `sessionCompleted`。不得因单个 unsupported action 静默丢弃后续 action，也不得把 session completion 误当成该 action 成功。
8. Swift contract fixture 必须与真实 Gateway 对齐：同一已知但无 handler 的 action 返回 `.failed`/`.actionFailed`、不可重试和脱敏 action-bound audit artifact，不再 false-success。
9. direct 与 WebSocket smoke 必须同时证明失败状态、审计绑定、无泄漏、无业务 artifact、无副作用及后续合法 action 可继续。
10. 同步协议、流程、测试和版本文档，并通过最新 `origin/main` GitHub Actions artifact 完成 Agent C 复判。

## 非目标

- 不为未支持 action 新增真实 handler；尤其不实现联系人、提醒、通知、外部 URL、Shortcuts、语音、后台刷新或桌面接管能力。
- 不删除或重命名 `ClawMobileActionKind` case，不修改 `claw.computer.control.v1` schema，不新增 action/event/artifact kind。
- 不改变已支持 handler 的现有审批、workspace、Shell、浏览器、桌面、提取、消息草稿或 Agent Loop 语义。
- 不把 handler 支持判定移到 iOS 作为唯一防线；即使 planner 或手机 profile 通常不会发送该 action，桌面 Gateway 仍必须独立 fail closed。
- 不把 unsupported handler 混同为 `action.approval == blocked` 或 envelope allowlist 未命中。已有 policy skip 语义保持不变，本轮新增的是“策略已允许但执行器不存在”的独立失败诊断。
- 不把 unsupported action 自动映射到 `genericAuditAction`、`auditLog` action、Shell、AppleScript、URL opener 或任何“最接近”的 handler。
- 不读取 artifact `file://` payload来驱动手机端判断，不新增 artifact payload viewer，不展示完整用户输入。
- 不实现持久化 handler registry、插件系统、动态下载执行器、远端工具发现或 capability negotiation 协议。
- 不顺手修复无关 planner、Mission Run UI、v0.63 会话关联或其他既有问题。

## 详细实现步骤

### 1. 建立固定 handler 支持集合

在 `Tools/claw-gateway-server.mjs` 定义一个靠近 action policy/dispatch 的常量或不可变集合，至少精确包含当前真实分派支持的 kind：

```text
runAgentLoop
observeScreen
controlBrowser
manageFiles
runShellCommand
extractData
operateDesktopApp
composeMessage
composeEmail
```

要求：

- 该集合只表示“存在固定 Node handler”，不等同于 envelope allowlist、平台能力、环境开关、审批状态或 v0.62 的 Agent Loop 推荐支持集合。
- `composeMessage` 与 `composeEmail` 可以继续共享 `messageDraftAction`，但二者都必须显式列入支持集合。
- `auditLog` 是 schema action kind，不代表允许任意动作通过 generic audit 成功；当前没有专用 action handler 时必须视为 unsupported。
- 保持 dispatch 为穷举显式 case。`default` 只能进入 fail-closed unsupported 路径或抛出内部一致性错误，绝不能成功。
- 推荐让支持判定与 dispatch 复用同一常量/helper，并添加静态可读的注释或 smoke 断言，降低集合和 switch 漂移风险；不要引入第三方依赖或复杂 registry。

### 2. 区分 envelope policy block 与 handler unsupported

执行判定顺序必须清晰且可审计：

1. 先保留现有 action approval 与 envelope `allowedActionKinds` 检查。
2. action 被 approval/envelope policy 阻断时继续使用现有 `skipped`/`actionSkipped` 语义，不调用 handler。
3. action 通过上述 policy 后，再检查固定 handler 支持集合。
4. 不支持时返回独立的 fail-closed result：`status="failed"`、固定 summary、`isRetryable=false`、一个 action-bound audit artifact。
5. 支持时才进入现有 handler switch；switch 的意外 default 也必须走同一 unsupported failure，不能 fallback success。

可以扩展 `actionPolicy` 返回稳定 decision code，也可以在 `runAction` 中单独执行 handler check；无论实现形式，测试必须能区分 `not-envelope-allowed` 与 `unsupported-action-handler`，且所有副作用 handler 只在两层检查都通过后调用。

### 3. 生成最小脱敏 unsupported audit

新增或收紧一个专用 helper，例如 `unsupportedActionResult` / `unsupportedActionAudit`，复用既有 `writeArtifact("auditLog", ...)`。建议固定 artifact title 前缀，例如 `unsupported-action-<index>.json`，并在 artifact event metadata 中提供安全字段：

```text
mode=gateway-unsupported-action
actionKind=<已知 enum raw value>
policyDiagnostic=unsupported-action-handler
schemaActionKnown=true
envelopeAllowed=true
handlerSupported=false
handlerExecution=blocked
businessSideEffectsAttempted=false
resultStatus=failed
retryable=false
safetyFlags=metadata-only,action-bound,handler-not-invoked,business-artifacts-not-written,tool-arguments-omitted,instruction-omitted,input-preview-omitted,target-omitted
```

字段名可按现有 metadata 命名风格微调，但必须满足：

- payload 和 event metadata 都能证明 action 绑定、handler 缺失、执行被阻断和无业务副作用。
- summary 使用固定文案，只允许插入安全 action kind；不要插入 action title、target、instruction、path、URL 或错误对象原文。
- artifact `redacted=true`。
- 不写原 `toolArguments` 的 key/value 列表；即使 value 看似安全也全部省略。
- 不沿用当前 `genericAuditAction` 的原始 payload。若 `genericAuditAction` 删除后无调用点，应删除它；若仍有明确合法用途，必须证明该用途不是 unsupported fallback，且不得扩大本轮范围。
- 审计 artifact 自身的 workspace 写入是允许且必需的审计行为；“无副作用”指没有业务 artifact、外部系统操作或 action handler 执行。审计写入失败沿用现有 Gateway 错误处理，不得把失败改报成功。

### 4. 保持事件与 session 语义

- unsupported action 可以保留现有 actionStarted，然后依次产生 action-bound `artifactStored` 和 `actionFailed`；最终事件的 `actionID`、`actionKind`、`resultStatus=failed` 必须一致。
- 同一 action 不得出现 `actionCompleted`、`approvalRequested` 或成功业务 artifact。
- `actionFailed.isRetryable` 必须为 false，避免手机端给出无意义自动重试信号。
- 继续处理 envelope 中后续合法 action，并保持 sequence 严格递增；最后产生 `sessionCompleted`。
- 不修改 replay guard：重复 task 仍应在 action handler/policy 前整体跳过，不为 replay action额外生成 unsupported failure 或业务 artifact。

### 5. 对齐 Swift Gateway fixture

更新 `Tools/ClawGatewayEventFixture.swift`：

- 建立与 Node Gateway 同语义的固定 supported kind 集合或集中 helper。
- `resultStatus(for:)` 对通过 envelope/approval 且无固定 Gateway handler 的已知 action返回 `.failed`，不要继续把这些 case 归到 `.succeeded`。
- `eventKind(for:)` 复用现有 `.failed -> .actionFailed`。
- unsupported fixture artifact 使用既有 `.auditLog`，action-bound、redacted，并附与真实 Gateway 同类的固定安全 metadata；不得模拟一个不存在的业务 artifact。
- unsupported summary 使用固定脱敏诊断，不插入 instruction/tool arguments。
- `isRetryable` 对 unsupported 必须为 false。
- fixture 对 approval blocked / envelope policy 的现有合同若没有实现，不要借本轮大幅重写；但不得让 fixture 对本轮目标继续 false-success。

本轮原则上不需要修改 `Claw/Core/ClawModels.swift`、`Claw/Services/ClawStore.swift` 或 `Claw/Views/ContentView.swift`：现有 failed/actionFailed/auditLog/通用 metadata review 足以表达结果。只有静态阅读证明现有 reducer 会把 unsupported `actionFailed` 错报成功、丢失 action 绑定或暴露 metadata 时，才允许做最小 Swift 修复，并同步 XCTest 与 LogicSmoke 对称覆盖；不得为了“看起来完整”新增专用 wire enum 或大块 UI。

### 6. Direct smoke 回归矩阵

在 `Tools/claw-gateway-direct-smoke.mjs` 新增独立、小型 envelope，至少包含：

- 一个 `ClawMobileActionKind` 已知、被该 envelope `allowedActionKinds` 明确允许、但不在固定 handler 集合中的动作。优先选择 `openExternalURL` 或其他不会与本地 planner 行为耦合的已知 case。
- 一个排在其后的合法、低副作用 handler action，例如 dry-run `observeScreen`，证明 unsupported 只失败当前 action且 session 继续。
- unsupported action 的 `instruction`、`inputPreview`、`target` 和 `toolArguments` 中放入唯一敏感 marker；`toolArguments` 同时放入看似可触发 file/shell/network 的字段，作为误分派哨兵。

必须断言：

1. unsupported action 有且仅有一个最终 `actionFailed`，actionID/kind 绑定正确、`resultStatus=failed`、不可重试。
2. 不存在同 action 的 `actionCompleted`、`approvalRequested` 或 policy `actionSkipped`。
3. 存在 action-bound、redacted `auditLog` artifact，title/metadata/固定 payload 证明 `handlerSupported=false`、`handlerExecution=blocked`、`businessSideEffectsAttempted=false`。
4. unsupported action 不产生 screenshot/browserTrace/fileDiff/commandOutput/extractedData/messageDraft/agentTrace 等业务 artifact。
5. workspace 中不存在哨兵文件或命令副作用文件；若使用本地 HTTP fixture，则目标 hit count 为 0。测试只使用小型临时 fixture，不访问公网。
6. 收集该 action 的 event summary、artifact title、metadata 和读取后的 audit payload，均不包含敏感 marker、raw URL/path/command/正文或 `toolArguments` 值。
7. 后续合法 action 正常到达其预期终态，session 最后产生 `sessionCompleted`，sequence 单调递增。
8. 现有 envelope allowlist 未命中场景仍为 skipped，不被误改成 unsupported failed。

### 7. WebSocket smoke 回归矩阵

在 `Tools/claw-gateway-smoke.mjs` 通过一次性 Gateway 增加等价场景，不得只复用 direct helper 后声称 WebSocket 已覆盖。必须断言：

- WebSocket envelope 的 allowlist 确实包含被测 unsupported kind。
- 推流事件中该 action 为 actionStarted -> action-bound artifactStored -> actionFailed，且不存在 actionCompleted。
- audit metadata/payload 固定、脱敏、不可重试；无对应业务 artifact。
- 副作用哨兵不存在；网络 fixture hit count 为 0（如果该场景配置网络哨兵）。
- 敏感 marker 不出现在与该 action 相关的推流 summary、artifact metadata 和 audit payload。
- 后续合法 action 仍完成，最终收到 sessionCompleted。

不要增加大数据、历史 artifact、外部网络依赖或真实桌面控制。direct 与 WebSocket 两套 smoke 都应覆盖核心 fail-closed 合同；可抽取测试 helper，但不能因此漏掉各自 transport 路径。

### 8. Swift/XCTest 评估要求

- 静态复核 `ClawGatewayEventFixture.swift` 生成的 unsupported `actionFailed` 是否能被现有 `ClawStore` reducer 计入 failed result、显示不可重试状态并保留 actionID/kind。
- 如果无需修改生产 Swift，则不强制新增大规模 UI 测试；应在现有 fixture 编译/运行入口或最小 XCTest/LogicSmoke 中验证 fixture 合同（以当前 CI 架构实际能覆盖为准）。
- 如果修改任何生产 Swift model/store/view，则 `ClawTests/ClawTests.swift` 与 `Tools/LogicSmoke.swift` 必须对称增加：unsupported failure 不计为 succeeded、不可重试、audit metadata 安全、Mission Run/结果行不显示注入 marker。
- 不读取 artifact `file://` payload来做手机端运行时判定；测试读取本轮 audit 文件只用于 Gateway smoke 验证写盘合同。

## 验收标准

- 固定 handler 支持集合与真实 `runAction` 显式分派一致，unsupported 永远不能进入 generic success fallback。
- 一个 schema 已知且 envelope allowlist 明确允许、但无固定 handler 的 action 最终为 `actionFailed`/`failed`/non-retryable；同 action 不存在 `actionCompleted`。
- unsupported action 只写 action-bound、redacted、metadata-only `auditLog`，明确 handler blocked 和 business side effects not attempted；不写业务 artifact。
- unsupported action 的 instruction、inputPreview、target、toolArguments 和敏感 marker 不出现在新增 summary、audit payload 或 metadata。
- 文件/Shell/网络/桌面/草稿/Agent Loop 副作用均未发生；smoke 通过文件不存在和可选 HTTP hit count 0 等可观察证据证明。
- 后续合法 action 仍按原策略执行，事件 sequence 单调，session 最终完成；sessionCompleted 不被解释为 unsupported action 成功。
- envelope/approval 未允许的 action 继续使用原有 skipped 语义，与 handler unsupported failure 可区分。
- Swift Gateway fixture 不再把无 handler 的已知 action报告为 succeeded，并保持 action 绑定、不可重试和脱敏 audit 合同。
- 未改变 schema/action/event/artifact kind，未扩大 Gateway 权限，未新增真实 unsupported handler。
- README、协议、flow、flowchart、test、update_log 与实现同步。
- 最新 `origin/main` commit 对应 GitHub Actions 通过，Agent C 下载的 artifact manifest 与 commit/run/attempt 一致并复判所有关键日志通过。

## 风险与处理

- **支持集合与 switch 漂移**：两处手写列表未来可能不一致。优先复用单一 helper/registry，并让 smoke 对当前支持集合和一个 unsupported case 建立回归；不要引入过度抽象。
- **把 unsupported 误归类为 policy skip**：会降低故障可见性。必须使用独立固定 diagnostic 和 actionFailed。
- **审计 artifact 自身泄漏输入**：现有 generic audit 会写 instruction/toolArguments，不能复用其 payload。新增 audit 必须字段白名单化并用 marker 断言。
- **“无副作用”被误解为不写审计**：本轮要求保留最小 audit artifact；禁止的是业务 handler、业务 artifact 和外部副作用。
- **单 action 失败中断整个 session**：会隐藏后续结果。unsupported result 应作为正常 action 失败事件返回，循环继续；只有审计落盘等基础设施异常才沿用全局错误路径。
- **fixture 与 Node 语义再次漂移**：两边至少共享同一书面支持列表和对称测试预期；不要让 fixture 把 unsupported 改成 skipped 或 succeeded。
- **手机端把 sessionCompleted 当全成功**：静态复核现有 reducer/result count；仅在确有缺陷时做最小 Swift 修复和对称测试。
- **CI 用例看似存在但未执行**：Agent C 必须从最新 artifact 日志确认新增断言实际运行，不能只看 workflow conclusion。
